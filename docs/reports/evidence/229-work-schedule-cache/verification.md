# 관리자 반복 근무 일정 캐시 검증

2026-11-24에 #230의 조회 쿼리 개선을 포함한 백엔드를 격리 환경에서 시험했다. 데이터는 운영 집계의 규모를 반영한 합성 데이터다. 애플리케이션 4 vCPU, Hikari 최대 커넥션 10, PostgreSQL 16.15, Redis 7.0.15, 활성 관리자 8명, 월 43건·연 516건의 날짜별 일정, 회원 3명의 반복 일정 13건을 사용했다. 부하 발생기와 앱·DB는 한 호스트의 별도 컨테이너로 분리했다.

## 커넥션 점유 재현과 회귀 테스트

수정 전에는 관리자 반복 일정 전체 조회 트랜잭션이 PostgreSQL 권한·버전 조회 후에도 열려 있어 Redis GET/SET 중 풀 커넥션을 점유했다. 실제 PostgreSQL과 Redis를 붙인 테스트에서 미스 GET과 SET, 히트 GET 직전 점유 수가 각각 `[1, 1, 1]`이었다. 수정 후 권한·버전 조회가 끝나면 커넥션을 반환하며, 같은 지점의 점유 수는 `[0, 0, 0]`이다.

Docker가 실행 중인 작업 환경에서 아래 명령으로 검증한다.

```sh
./gradlew test --tests '*WorkScheduleCacheIntegrationTest'
./gradlew build
```

회귀 테스트는 저장·삭제와 이름·팀 변경, 롤백, 관리자 권한 강등, 이전 버전의 늦은 캐시 채우기, Redis 정지 중 PostgreSQL 폴백, Redis 복구 후 최신 일정 반환을 확인한다.

## Gatling 장애 시험

기존 Redis 구현과 JDBC 트랜잭션 경계를 수정한 구현에 각각 같은 부하를 넣었다. 관리자 한 흐름은 첫 진입, 다음 달 두 번, 개인 전환으로 총 GET 10건이다. 실제 호출에는 전체 반복 일정과 전체 날짜별 일정 GET을 사용한다. 매초 51.2개 흐름으로 요청 합계 목표 512 RPS를 맞췄다. 15초 램프 뒤 30초 정상 단계의 시작 10초 후, 격리 Redis 컨테이너를 약 8초 동안 정지했다.

| 회차 | Gatling 요청 수 전 / 후 | 타임아웃 전 → 후 | Hikari 대기 최대 전 → 후 | 첫 진입 날짜별 p95 전 → 후 | 첫 진입 반복 p95 전 → 후 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 15,360 / 15,360 | 540 → 0 | 190 → 0 | 2,448 → 2ms | 2,694 → 103ms |
| 2 | 15,360 / 15,360 | 576 → 0 | 190 → 0 | 2,810 → 2ms | 2,796 → 102ms |
| 3 | 15,360 / 15,360 | 470 → 0 | 190 → 0 | 2,657 → 2ms | 2,679 → 103ms |

1차는 2,048 RPS 워밍업과 3,328 RPS 정상 부하를 먼저 실행했다. 2·3차는 각 빌드를 재기동하고 동일한 응답 건수와 권한 확인 후 512 RPS 램프부터 진행했다. 2차는 기존 → 개선, 3차는 개선 → 기존 순서다. p95는 Redis 정지와 복구를 포함한 정상 단계의 Gatling 클라이언트 측정값이다. Hikari 대기 최대는 Prometheus/Grafana 수집값이다.

## 조회 부하 중 일정 등록

개선 빌드에서 Redis ON과 512 RPS 조회 부하를 유지하면서 일반 회원의 반복 일정 1건을 등록했다. 45초 정상 단계에 회차별로 Gatling 조회 23,040건을 실행했고 모두 성공했다. 저장 응답 완료 이후 독립 관리자 세션 8개의 첫 동시 조회와 뒤이은 표본을 전체 내용 기준으로 대조했다.

| 회차 | 첫 동시 조회 정확 | 부하 중 전체 응답 일치 | 새 Redis 키의 미스 | 등록 포함 8초의 반복 일정 서버 p95 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 8/8 | 80/80 | 9 | 2.31ms |
| 2 | 8/8 | 80/80 | 9 | 1.18ms |
| 3 | 8/8 | 80/80 | 10 | 1.33ms |

정상 등록 후에는 이전 13건과 새 일정 1건이 반환됐고, 대상 회원·요일의 PostgreSQL 행은 1개였다. 잘못된 시간 범위의 수정은 세 번 모두 HTTP 400으로 거절됐으며 DB 버전과 정규화된 전체 응답은 그대로였다. 종료 후는 테스트 데이터를 삭제하고 원래 응답을 확인했다. 등록 전후 Hikari 대기 수집값은 0이었다. 서버 p95는 Prometheus 히스토그램 추정치다.

## 정상 Redis ON/OFF

같은 수정 후 JAR에서 3,328 RPS 목표로 Redis OFF와 ON을 한 번씩 실행했다. 양쪽 모두 실제 처리율 약 3,328 RPS와 오류 0건이었으며 PostgreSQL SELECT/s는 6,761.5에서 4,296.7로 약 36% 감소했다. 운영 환경의 응답 시간이나 최대 처리량을 추정하는 데 이 결과를 사용하지 않았다.
