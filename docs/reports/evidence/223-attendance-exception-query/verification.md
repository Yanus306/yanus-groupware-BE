# #223 근태 예외 목록 최적화 검증

2026-11-17에 기존 `dev` 커밋 `210b46324bef885350db6c8e64ee38ab3c1c581b`과 이 커밋 기반 `feat/#223` 로컬 구현을 비교했다. 두 버전의 JDK는 21.0.10이고, 각각 별도 PostgreSQL 16.15 Testcontainers에 같은 Flyway V27을 적용했다. 정확한 운영 소스·Gradle 설정 지문은 결과 JSON의 `production_source_fingerprint` 필드에 있다.

## PostgreSQL SQL 호출

| 활성 회원 | 시나리오 | 수정 전 SELECT + INSERT | 수정 후 SELECT + INSERT | 합계 변화 |
| ---: | --- | ---: | ---: | ---: |
| 10명 | 첫 조회 | 63 + 10 | 6 + 10 | 73 → 16 |
| 10명 | 같은 날짜 재조회 | 63 + 0 | 6 + 0 | 63 → 6 |
| 100명 | 첫 조회 | 603 + 100 | 6 + 100 | **703 → 106 (84.9% 감소)** |
| 100명 | 같은 날짜 재조회 | 603 + 0 | 6 + 0 | **603 → 6 (99.0% 감소)** |

같은 팀에서 월요일 반복 일정이 있고 출결·날짜별 일정이 없는 fixture를 사용했다. 첫 요청은 예외가 없는 날짜에서 시작하고, 재조회는 첫 요청의 저장이 끝난 날짜에서 실행했다. 개선 이후에는 회원·주간 일정·날짜별 일정·출결·기존 예외 키·최종 목록을 읽는 SELECT 6회가 양쪽 크기에서 같았다. 각 경우의 반환 건수와 저장 건수는 회원 수와 같았다.

합계는 `pg_stat_statements`에서 읽은 PostgreSQL의 DML 호출 수다. 개선 후 Hibernate prepared statement 카운터는 첫·재조회 모두 6회지만, 첫 조회의 JDBC 배치 INSERT 100회는 Hibernate 바깥에서 실행돼 DB 합계에 따로 더해진다. 네트워크 왕복 횟수는 이 표에 포함하지 않았다. [수정 전 쿼리 원본](benchmark-baseline.json) · [수정 후 쿼리 원본](benchmark-optimized.json)

## HTTP 지연 시간

| 100명, 동시성 1 | 수정 전 p50 | 수정 후 p50 | 수정 전 p95 | 수정 후 p95 | p95 변화 | 오류율 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 첫 조회 | 195.32 ms | 10.68 ms | 263.16 ms | **15.90 ms** | **94.0% 감소** | 0/100 → 0/100 |
| 재조회 | 157.09 ms | 5.61 ms | 273.86 ms | **7.05 ms** | **97.4% 감소** | 0/100 → 0/100 |

같은 호스트에서 기준본과 개선본을 차례로 띄웠다. 각 버전과 시나리오에서 동일한 JWT GET을 20회 워밍업하고, 한 번에 한 요청씩 100회 측정했다. 클라이언트는 루프백 HTTP 연결을 재사용하고 응답 본문이 수신될 때까지 시간을 쟀다. 첫 조회 표본마다 해당 날짜 예외를 지우는 작업은 계측 밖에서 실행했다. 재조회는 예외 100건을 미리 만들었다. 지연 시간 계측 동안 Hibernate 통계는 끄고, p95는 성공 100건을 정렬한 뒤 95번째 표본을 사용했다. 각 호출에서 HTTP `200`과 응답 항목 100건을 확인했다. 수치는 이 로컬 실행의 표본이다.

## 동시 조회와 API 계약

| 검증 | 관측 |
| --- | --- |
| 100명 동시 첫 조회 | 두 INSERT가 같은 테이블 락에 대기한 것을 확인했다. 기준본은 `200`·`500`, 개선본은 `200` 두 건이다. 개선본의 두 응답은 예외 항목·요약이 같고 DB에는 예외 100건이 남았다. |
| 기존 상태를 가진 행과 신규 후보가 섞인 동시 조회 | HTTP 통합 테스트에서 두 요청 모두 `200`을 반환했다. 날짜·회원·유형당 한 행이며 승인·반려 상태와 기존 메모가 보존됐다. |
| 필터와 요약 | 팀·유형·상태를 모두 지정한 요청은 목록 1건과 `filteredCount=1`을 받았다. 데이터 전체의 `totalCount=4`, `openCount=2`, 출근 누락 3건·일정 없음 1건도 확인했다. |
| 경계와 공유 코드 | 출결 연결이 없는 누락 건도 반환한다. 잘못된 유형·상태는 400과 쓰기 0건이다. 자동 퇴근은 선택한 회원만 처리하고, 생성 트랜잭션 롤백 시 예외가 남지 않는다. |

수정 전에 작성한 회귀 테스트는 SELECT 횟수 `[63, 63, 603, 603]`과 동시 조회 `200`·`500`으로 실패했다. 개선 후 같은 테스트가 통과했다. [수정 전 실패 결과](gradle-red.json) · [전체 재현 방법](reproduction.md)

## 회귀 테스트

근태 예외 통합·서비스·판정 테스트를 통과했다. 전체 Gradle 테스트는 JUnit 기준 **43개 스위트, 291개 테스트 모두 통과**했고 실패·오류·건너뜀은 각각 0건이다. Gradle 빌드로 실행 JAR을 생성했다.

클린 빌드에서 Persona Harness의 `npx ph workflow finish implement --assurance cooperative`가 `PASS`를 반환했다. 이 결과는 해당 로컬 실행 범위에 해당한다.
